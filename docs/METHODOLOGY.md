# Methodology

## What is being checked
Two Databricks cost models (ANZ and USA smart-metering platforms) price each use case as

```
cost = clusters x minutes/run x DBU/hr x $/DBU x runs/day x days   (+ VM cost for classic compute)
```

The inputs that were estimated rather than measured are **minutes per run**, **cluster counts at each meter tier**
and the **serverless DBU rating** (a serverless node billed at about 2.34x its classic rating in a Databricks cost calculator;
about 1.0x in the original sizing's recorded runs). This repository implements each use case on synthetic data so those
three inputs can be measured.

## Approach
1. **Synthetic data** (`src/00_generate_data.py`, `src/common.py`): `n_interval_meters` meters (default 100,000) with 5-minute
   readings for `history_days` (default 7), a register of `n_platform_meters` (ANZ default 600,000), conversation logs
   (6 per meter per day) and a 12-month daily-peak history. Known signals are seeded so every detector has something to find:
   voltage excursions, poor-comms meters, transformer outages, EV-like and PV-like load shapes.
2. **One job per use case** (`resources/jobs.yml`, generated by `scripts/gen_jobs.py`). Serverless billing is only attributable to
   a job *run*, so each use case runs as its own job; `bench_all_anz` / `bench_all_usa` run them one after another.
3. **Timing** - every notebook records wall-clock seconds per step to `bench_results` (`common.Bench`).
4. **Billing** - `src/90_report.py` joins runs to `system.billing.usage` by `job_run_id` and divides a job's DBUs across its steps by runtime.
5. **Comparison** - measured DBUs are scaled linearly to the model's tier (benchmark meters -> model meters) and compared with the
   model's DBUs per run from `docs/model_assumptions.csv`. Continuous (always-on) lines are checked by *throughput*: backlog drain
   rows/second per node versus the rows/second the tier requires.

## Mapping of model lines to compute
| Model | Benchmark |
|---|---|
| Azure D4ds_v5 / D8ds_v5 / D16ds_v5 (4 / 8 / 16 vCPU) | AWS m5d.xlarge / m5d.2xlarge / m5d.4xlarge |
| Azure L8s_v2 / L32s_v2 (storage optimised) | AWS i3.2xlarge / i3.8xlarge (not run; serverless ignores node type) |
| Jobs Serverless | serverless jobs compute |
| DBSQL Serverless Small / Medium | serverless SQL warehouses `sm-bench-small` / `sm-bench-medium` |

## Limits - read before quoting numbers
* **AWS vs Azure.** The workspace used for the benchmark is AWS us-east-1; the models price Azure. DBU quantities are comparable
  (same instance families, same serverless engine); dollar rates and VM prices are not, so the report compares **DBUs and minutes**, not dollars.
* **Synthetic data.** Row widths (16 / 21 doubles in flat JSON, ~330-450 bytes) are close to, but not the customer's, payload. The model notes
  the original sizing assumed ~0.7 KB messages.
* **Stand-in algorithms.** The customer's forecasting, EV/PV detection and outage models are not available. The notebooks use
  Spark-native rule/aggregation stand-ins, which set a **floor** on compute; real ML models will cost more.
* **Linear scaling.** 100k meters is extrapolated to 0.5M-6M assuming linear cost. Fixed overheads (start-up) are over-counted and
  shuffle/skew growth is under-counted; treat the model-vs-measured ratio as roughly +/-50%.
* **BI serving** is priced in the model as warehouse uptime hours (3.5 h per workday). The benchmark measures query latency per
  warehouse size and the daily refresh duration; it cannot measure how many hours users actually keep a dashboard open.
* **Frequency gaps** flagged in the USA model (voltage alarms, EV/PV disaggregation, outage detection are continuous in the
  customer file) are implemented as daily batches here too, so they are *not* validated by this benchmark.
